# Codex 主管与 Pi Worker

本 Skill 在主管侧使用，配合已连接的 pi-durateam MCP。无需在目标项目先安装脚本；不要假设 Worker 继承当前对话。

## 成本目标与主管边界

本 Workflow 的首要目标是用低价 Pi 模型完成具体执行，减少 GPT 总投入。GPT 负责规划、任务拆分、接口协调、状态判断与按证据验收。遇到卡点可提供思路、核对契约、构造最小反例，必要时围绕具体失败定向定位 Bug；默认不直接编写或重写业务实现。具体修复优先交回 Pi；无法推进时报告流程局限，不用隐性接管掩盖失败。

原生 Supervisor 只接收必要任务、Skill 入口和环境信息，避免继承整份长聊天。正常监督按阶段或异常进行，不逐步分析工具轨迹。运行中只返回状态/计数，完整 Trace 仅在结束或具体故障时保存到文件，避免轮询日志反复进入主管上下文。先用确定性检查/现有测试和简短摘要判断，仅在具体失败或风险处读取必要片段，不默认通读所有 Worker 源码。新增测试/修复代码也应优先由 Pi 执行，独立验收与实现任务保持分离，已有固定验收可直接复用。

成本记录必须包含 Root、原生主管、Pi、返工和集成，区分一次性搭建/试验成本与每轮日常成本。可从本地 rollout 的 token_count 累计计数按任务时间窗采集用量；脚本见项目可选工具 collect_codex_usage.py。不要上传完整会话，不重复累计快照，缓存是输入的子集。订阅额度/账单或可比直接实现基线缺失时，成本收益仍标为未验证；SDK cost=0、没有亲写业务、测试通过均不能替代省钱证据。监督开销接近直接实现时应简化交接/阅读或改变流程，而非继续增加 GPT 角色。用户暂缓费用对照时，继续技术验收并保留费用未知，不以缺少账单基线阻塞所有迭代。

独立验收通常接在可运行候选之后；只有需要并行调查真实风险时才提前启动，避免单为重复规划或空等增加一层模型调用。已有验收上下文保留到候选可测时续接。

## 任务与执行能力

先结合用户目标和代码情况明确任务目标、必要背景、负责范围、完成标准。大型项目先明确影响并行的接口契约、数据/状态不变量、事务边界与验收，再按依赖和文件责任拆分，为写入任务分配独立 Worktree/运行资源后派发。共享接口与文件指定负责人，有依赖的任务按明确基线衔接；不预先规定模块内部全部实现。简单任务直接用 prompt；较复杂的任务才使用清单或任务文件。允许 Worker 自主选择实现、搜索、AST、LSP、调试和测试方法，不逐步规定操作。默认给予较高实现自由度，约束集中在目标、共享契约、写入责任与可验证交付；通过真实失败调整必要边界，不将一次测试失误普遍扩张为编码步骤限制。

编码任务启用 `extensions:true`，传入服务端已授权的常用读写、bash 和已安装扩展工具，让 Worker 能自测。白名单只是可用能力上限，不表示任务自动获得工具；spawn 的 tools 仍需明确列出。纯调查使用只读能力。外部服务按任务用 nativeMcp/mcpServers 选择，不凭空猜服务和工具名称。

本机专属环境为 `/Users/YOU/pi-durateam-config`，默认 DeepSeek 模型已配置，思考程度以专属 settings 为准（当前 max）；无特殊需要省略 model/thinking，避免旧示例覆盖新默认。更换模型或环境时通过 models（必要时 init）核实。 核对模型配置的thinkingLevelMap与提供商档位语义，避免把兼容别名当独立强度；本机该DeepSeek的xhigh等效high，max才是更高实际档。 若本次验收需要请求级证据，确认观测器实际命中请求，不以注入代码或配置标签代替；只记录档位等安全元数据，调试注入不是日常派工前置。不要重装或覆盖已有 MCP 来执行普通任务。

将必要的项目说明放入 resources.contextFiles，相关 Pi Skill 的绝对 SKILL.md 路径放入 resources.skills；后者需要 read 或 bash。将任务材料作为 prompt 或 attachments 提供。只传与执行有关的指令，避免让 Worker 接收整套主管调度流程。没有项目 Worker 文档时，可直接在 prompt 中约定自主完成、自测、交付结果、由主管提交集成。

## 派发前的一致性检查

先核实当前 MCP 工具参数、预算上限、绝对 cwd 和附件存在性；同时核对实际 Worker cwd 下需要的项目级配置，不能假设父目录或专属环境文件自动继承。例如 .pi-lsp.json 由扩展按cwd读取，约定的autoStart/autoInjectDiagnostics需要在新工作区准备，已有servers等内容应保留；启动后补文件不代表既有会话已重载。尽量让整批任务在启动任何一个 Worker 前完成可用的校验。复杂批次分发或续接任务副本后，核对实际cwd中的任务/契约版本或预期SHA；源目录更新不代表隔离副本已同步，修订时先保留旧版并通知受影响Worker。基础类型/预算检查不能宣称覆盖模型可用性、状态等所有语义；新任务批次可利用 spawn_batch 的服务端整体校验，混合续接应拒绝同批重复 sessionId。不要猜超出实际 schema 的预算后反复重试。

工作区准备与派发分开：只有目录、仓库/基线与写入责任已确认才派写入任务。宿主 Worktree 请求未返回时跟踪原句柄并核对实际清单，不因观察超时重复创建。确认原调用终止并检查没有已创建产物后，才按授权改用独立 clone/其他隔离目录，记录它与 Worktree 的差别。控制侧契约若从单 Worker 改成多 Worker，要删除矛盾的旧所有权说明、记录版本，并明确通知运行中的 Worker；不能只在末尾追加新规则。

## 并行与监督

- 按依赖和写入冲突拆分并行任务，写入 Worker 使用各自工作区。优先复用宿主已有 Worktree 能力和当前合适工作区；只读任务不必为了形式创建 Worktree。
- 本机新启动的 MCP 服务进程并发上限为 5、单次 batch 上限为 5；这是容量上限，按依赖、写入冲突和资源实际选人数，不默认派满。限制按服务进程计，不代表多个客户端合计只有 5 个；旧进程可能仍使用原值，应核实实际服务限制，超出时分批。用 spawn/spawn_batch 启动长任务，wait 等待；根据返回的 continueIds/nextAction 和实际状态继续。
- 遇到等待中的问题用 answer 回答对应 requestId；执行中用 steer 纠偏，结束后用 follow_up 提供具体失败证据。不要假定 finish 等于成功，检查 state/error/termination/answerState。 MCP 返回 isError 或业务拒绝也必须判失败，不能以外层脚本 exit0 视作投递成功；控制运行中会话应使用拥有该会话的连接，并核实工具响应，跨进程读取状态不等于有权 steer。修改磁盘执行器不会使既有进程自动加载新的控制通道。
- follow_up 不能随意改变旧授权；需要不同工具或模型时按实际支持的接口新建或 fork。停止无进展的重复修复，由主管调整任务或定向诊断，不自动演变为大范围业务代写，也不固定每项任务的返修轮数。
- 先看摘要、修改清单和验证结果，必要时再查详细轨迹，避免主管重复阅读 Worker 的全部过程。

大型任务宜以可运行增量衔接：尽早完成一次构建、启动和关键路径检查，再扩展规则与测试。若预算耗尽时仍只有未编译源码，续接时先建立这条验证路径，必要时重新拆分；不要仅扩大预算重复原方式。到期中止先保存现场并核实 termination、剩余工作和 canFollowUp，能续接时沿原会话推进，不将中止误报完成，也不因观察超时另起重复 Worker。检查点按任务风险设定，不要求主管逐行监督。

验证新 Agent SDK 的会话续接/分支时，核对实际调用的 resume/fork 参数；记忆探针不在后续输入泄露答案，并排除从文件重新取回答案。先区分桥接漏接与上游限制，不以放宽断言代替定位。

## 新任务与上下文延续

接到新任务先判断现有 Worker 的模块知识、调查/失败记录、工作区基线与当前状态是否有用，再决定续接、排队或新建。相关模块的增量需求、返修、测试扩展，优先复用原会话；原 Worker 忙于相关工作时，根据依赖等待或通过其所属连接协调，避免给同一会话并发派互相冲突的任务。已经结束且仍可续接时用 follow_up，不为每个新任务默认 spawn。

独立并行模块需要更多产能、原上下文无关或已经过时、反复陷入同一错误假设，或验收要求与实现者独立时，再考虑新 Worker。不要为了复用强迫一个会话包揽不相关任务，也不把全部长聊天复制给新会话。续接前提供必要的契约/提交变化和增量目标，确认旧工作区跟上集成基线；相关决策与检查结果适量留在项目文件中，使会话过期后仍可用简短交接恢复知识。人数、是否续接由主管按任务判断，无需每次询问用户。

## 卡点升级：允许定向帮助，避免重新理解整个项目

日常按摘要、完整变更路径清单、测试/构建退出码和集成结果判断，不默认读取完整 diff 或完整源码。测试通过不是所有质量/风险已经证明；共享契约、事务、一致性等相关关键点可根据具体风险做局部审查。

同型工具调用连续出现缺字段、JSON截断或输出上限时，先定向检查一次失败及其参数规模；可缩小单次payload或改用有效调用方式，并先保存已有可验证增量，避免不断整份重试或只追加预算。仅在出现这种实际故障时纠偏，不规定所有Worker日常都要分块编码，也不默认降低模型思考程度。

Worker 遇到反复同因失败、调查没有收敛、契约歧义或跨任务冲突时，提交精简诊断包：最小复现、实际/预期、失败命令和日志路径、相关接口/符号、已尝试假设及其结果、需要主管判断的问题。不要默认传整个聊天或全量代码。

主管按需要逐级介入：先核对需求/契约与失败假设并给方向；仍无法推进时读取失败栈、相关函数和直接调用方/数据结构；必要时沿证据扩展一小段调用链，直接定位 Bug。每次扩展阅读围绕一个明确问题，得到结论就交回 Pi 修复并复跑原验收。不要为节省阅读而拒绝必要调查，也不以“需要定位”为由通读全部 Worker 实现。无新证据时重审拆分/假设，避免无限扩大搜索。

可以让独立调查者处理复杂定位，但其输入与成本同样计入总投入，不能用增派强模型假装消除了主主管开销。对外报告介入原因、读取范围和定位结论即可，不必重放完整推理过程。大范围重写或改变技术路线另行明确，不等同于本次允许的定向定位。

## 验收与复用

Worker 应独立实现和自测，交付实际变更、检查命令及真实退出码、未验证项；截断日志时仍需保留测试本身的退出码。服务类检查由测试执行器管理启动、readiness、超时、停止与回收，避免直接无期限 wait 常驻服务；挂起时先定位具体命令和进程，保留现场后只回收任务自己的进程。每次检查由执行器自动生成独立日志并记录真实退出码，批次结果追加保存，不能依赖 Worker 手工命名或最终文字总结；汇总项数、日志存在性和退出码应可核对。发现日志覆盖时明确证据缺口并复跑，不能后补成首次证据。测试预期有误时依据原合约说明修正，不能把改变验收当作修复业务。 契约未规定的字段顺序、额外字段处理等行为先记录观察，不自行增加硬性预期；将需求缺陷、实现缺陷和测试自身假设分开判断。项目可选 run_check.py 可保存完整证据、仅输出简短元数据。临时探针使用任务目录或唯一临时目录。主管按风险检查实际 diff 并复跑必要验收；多个任务集成后验证组合行为。 多人新增测试后核对实际测试发现范围是否包含新文件，避免旧显式列表遗漏模块却把子集绿色当全量通过。 同时排除归档或验证副本，避免测试被重复发现、计数失真。不要因 Worker 自报成功直接宣布完成。

当 Worker 新建或修改自测框架/执行器时，加入独立负对照：故意错误的断言或已知违规行为必须使真实命令非零退出，恢复后再通过。负对照需说明故意注入的错误断言/行为及实际命令；普通编码或返修回归不能仅因作者事后称呼而算作有意负对照。日志显示 FAILED 但命令 exit0 不是有效失败证据；测试 helper 不应意外覆盖 fail/run/assert 等框架方法。Python unittest 可用项目可选 check_unittest_integrity.py 检查多种错误断言；它不代替业务测试。独立验收避免复用被审查方自测helper。 若主管保留不向实现者公开的验收，交接时明确其读取边界，仅交付必要最小反例；普通项目测试仍可自由阅读。实现者已读/复制时如实降低未见验收的声明，不能用其自跑代替独立执行，必要时补少量未提供的新变体。 验证某项约束时保持其他条件有效，避免其他拒绝原因掩盖目标：例如测旧token时保持同一owner，单看409不能证明fencing。

Sanitizer分别记录实际执行的ASAN、UBSAN、泄漏等范围；平台不支持的项标为未验证，不把关闭某检测后其他检查通过写成所有内存风险已消除。

使用用户已经授权的提交和集成范围，不自动推送或扩大发布范围。工具白名单、Skill 和 Worktree 都不是 OS 沙箱。

复杂并行批次若需要固定任务 JSON、路径门禁和脚本管理，按需读取 [严格模式](references/strict-workflow.md)。普通任务不必先部署该模式。根据真实返工、耗时、用量和失败案例改进流程，未验证的模型偏好不要固化成通用规则。
